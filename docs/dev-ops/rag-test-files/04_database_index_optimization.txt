标题：数据库索引优化笔记

数据库索引的本质是用额外存储换取查询速度。MySQL InnoDB 中最常见的是 B+Tree 索引。B+Tree 的叶子节点按键值有序，并通过链表连接，所以它既适合等值查询，也适合范围查询。主键索引的叶子节点保存完整行数据，二级索引的叶子节点保存索引列和主键值，因此二级索引命中后可能需要回表。

设计联合索引时要遵守最左前缀原则。例如索引 (tenant_id, status, created_at)，可以支持 tenant_id 查询，也可以支持 tenant_id + status 查询，还可以支持 tenant_id + status + created_at 范围查询。但如果查询条件只有 status，通常无法充分利用这个联合索引。范围条件之后的列也可能无法继续用于有序定位。

覆盖索引可以减少回表。如果查询只需要 id、status、created_at，而这些字段都在二级索引中，数据库可以直接从索引读取结果。对于高频列表页，覆盖索引通常非常有价值。不过索引不是越多越好，过多索引会增加写入成本、占用磁盘，并让优化器选择变复杂。

慢查询排查通常从 explain 开始。重点看 type、key、rows、Extra 等字段。type 从好到坏大致包括 const、ref、range、index、ALL。Extra 中出现 Using filesort 或 Using temporary 不一定必然糟糕，但在大数据量分页排序场景需要重点关注。深分页可以通过 seek pagination 优化，例如使用 where id > lastId order by id limit 20。

常见误区包括：在低区分度字段上单独建索引、对索引列使用函数导致索引失效、like '%keyword' 无法使用普通 B+Tree 前缀、隐式类型转换导致索引失效、order by 字段和 where 字段索引顺序不匹配。优化时应该结合真实查询频率和数据分布，而不是机械套公式。

可用于召回测试的问题：
1. 什么是覆盖索引，它为什么能减少回表？
2. 联合索引的最左前缀原则是什么？
3. 深分页可以用什么方式优化？
